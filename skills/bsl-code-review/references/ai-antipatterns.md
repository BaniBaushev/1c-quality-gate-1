# Антипаттерны кода, порождаемого языковой моделью

Типовые своды стандартов описывают ошибки, которые делают люди. Этот файл — про ошибки,
характерные для кода, который пишет модель. Человек их обычно не делает, поэтому ни один
типовой свод их не покрывает, а статический анализатор не видит: код синтаксически безупречен.

Каждый пункт получен из реальной переработки сгенерированного кода разработчиком. Проверять
**всегда**, при любой глубине прогона, наравне с антипаттернами производительности.

Идентификаторы `qg:AI-NN` используются в записях следа.

---

## Группа A. Портят данные или не работают

### AI-01 · Запись набора с удалением по неполному отбору 🔴

**Что искать:** `НаборЗаписей…Записать(Истина)` там, где отбор задан не по всем ключевым
координатам. Для периодического регистра — отсутствие `Период` в отборе.

**Почему это опасно:** `Записать(Истина)` сначала **удаляет из базы все записи,
удовлетворяющие установленному отбору**, и лишь затем пишет набор. Отбор по части измерений и
без периода уничтожает всю накопленную историю по этим измерениям, а не «перезаписывает
текущий снимок». Симптом обнаруживается спустя недели — когда историю уже не восстановить.

**Как правильно:**

- перезапись снимка на конкретный момент — `Записать(Истина)` с отбором по `Период` **и** всем
  измерениям, постоянным для набора; измерение, варьирующееся внутри набора, в отбор не
  ставится, иначе удаление станет точечным и не вычистит устаревшие строки;
- одиночная запись — `СоздатьМенеджерЗаписи()`: ключ включает период и измерения, стереть
  историю физически не может;
- накопление новых срезов — `Записать(Ложь)`;
- период задавать детерминированно (дата документа, дата события), не `ТекущаяДатаСеанса()` —
  иначе повторный запуск плодит дубли;
- беспериодную перезапись нельзя называть идемпотентной: она деструктивна.

**Признак в диффе, который часто сопровождает ошибку:** в одном модуле соседние процедуры
используют разные режимы записи, причём у одной стоит комментарий вида «здесь `Истина` стёрло
бы всё». Самопротиворечивый код — сигнал, что режим выбран не по механике, а по совпадению.

### AI-02 · Чтение реквизита ссылки через точку 🔴

**Что искать:** `Ссылка.Реквизит` в новом или изменённом коде, где объект не нужен целиком.

**Почему:** обращение через точку загружает **весь объект** — все реквизиты и табличные части.
Для единичного чтения это лишняя нагрузка и заполнение кеша.

**Как правильно:** `ОбщегоНазначения.ЗначениеРеквизитаОбъекта(Ссылка, "Имя")`, а для нескольких
полей — `ЗначенияРеквизитовОбъекта(Ссылка, "Имя1,Имя2")` одним вызовом (возвращает структуру). Точка допустима,
только если объект уже получен как объект (например, в обработчике события) либо это поле выборки запроса.

**Отдельно про ревью:** «так написан соседний код» не является основанием понизить эту находку.
Легаси чинится отдельно; новый код пишется правильно сразу. Идиома окружения — не аргумент
против механики платформы.

### AI-03 · Фабрикация метаданных в рантайме и обход API подсистем 🔴

**Что искать:** программное создание видов характеристик и дополнительных свойств из кода;
прямая запись в системные регистры библиотеки через менеджер записи в обход её публичного API.

**Почему:** создание метаданных во время выполнения хрупко — зависит от порядка инициализации
и ломается при обновлении. Обход публичного API подсистемы создаёт незаявленный контракт:
библиотека о ваших данных не знает и не обязана их сохранять.

**Как правильно:** сначала инвентаризировать существующие реквизиты объекта — нужное часто уже
есть в типовой конфигурации. Если нужен новый реквизит, он добавляется как объект метаданных, а
не из кода. Запись значений — только через публичное API подсистемы.

**Диагностический признак:** мысль «стандартное API отбросит мои данные» означает не дефект
API, а неверную модель данных. Чинить нужно модель.

### AI-04 · Отчёт о проверке, которая не прогонялась 🔴

**Что искать:** утверждения «проверено», «зарегистрировано», «собирается», «проходит» без
следа фактического прогона.

**Почему:** ложно-уверенный отчёт хуже честного «не проверял» — он закрывает вопрос фальшивой
зеленью. Именно этот антипаттерн делает бессмысленной любую систему контроля качества, включая
эту.

**Как правильно:** такие слова допустимы только после реального прогона — поиска по файлу
конфигурации, настоящей сборки, трассировки по фикстуре. Не прогонял — так и пиши.
В следе прогона для этого есть отдельная запись `not_verified`.

Частный случай той же ошибки: строить логику на догадке о семантике полей внешнего контракта
(«это, наверное, GUID», «оно приходит в этом методе»). Тип, наличие и смысл поля сверяются по
реальной фикстуре **до** написания кода, иначе код переписывается два-три раза.

### AI-05 · «Зелёная» сборка принята за доказательство компилируемости 🔴

**Что искать:** вывод «код компилируется» на основании успешной загрузки конфигурации из
файлов, выгрузки, валидатора XML или статического анализатора.

**Почему:** загрузка и выгрузка конфигурации работают со **структурой** и не компилируют тела
модулей. Синтаксическая ошибка внутри процедуры проходит их все, а всплывает при инициализации
модуля в базе. Статический анализатор тоже толерантен к части конструкций, где платформенный
компилятор строже.

**Как правильно:** компилируемость подтверждает только проверка конфигурации платформой
(`/CheckConfig`) либо реальный прогон в базе. Если ни то ни другое не выполнялось — запись
`[qg not_verified: dimension=compilation, reason=no_platform]`.

**Конкретная ловушка, породившая правило:** у блочных операторов (`КонецПопытки`, `КонецЕсли`,
`КонецЦикла`) точка с запятой необязательна, **пока они последние в своём блоке**. Как только
после такого оператора вставляется ещё один, он перестаёт быть последним — и требует `;`.
При вставке кода после закрывающего оператора всегда проверяй строку прямо над местом вставки.

## Группа B. Раздувают код и множат точки отказа

### AI-06 · Самодельный флаг отмены вместо `Отказ` 🟠

**Что искать:** выходные параметры вида «ЕстьПроблемы», структуры-мешки с полями «Прервать» и
«Текст» там, где семантика — обычная отмена операции.

**Почему:** `Отказ` — конвенция платформы и библиотек, её понимают все стандартные обработчики
и все читатели кода. Своя конструкция требует изучения и не стыкуется с типовым поведением.

**Как правильно:** выходной параметр провала называется `Отказ` и имеет тип Булево; подробности
пишутся в журнал регистрации.

### AI-07 · Отсутствие `Знач` у немутируемых входных коллекций 🟠

**Что искать:** параметры-структуры, массивы и таблицы значений без `Знач` в функциях, которые
их не изменяют.

**Почему:** коллекции передаются **по ссылке**. Без `Знач` функция может незаметно изменить
коллекцию вызывающего — дефект воспроизводится редко и ищется долго.

**Как правильно:** входы только для чтения объявляются как `Знач ИмяПараметра`.

**Смежная ошибка:** `Знач` — модификатор **параметра**, а не локальной переменной.
`Знач Переменная = …` внутри тела процедуры даёт синтаксическую ошибку.

### AI-08 · Разбор одного и того же payload в нескольких местах 🟠

**Что искать:** пер-польные аксессоры, размазанные по коду сопоставления — отдельная функция
для получения строки, отдельная для даты, отдельная для числа, и так по всему маппингу.

**Почему:** россыпь аксессоров даёт дублирование, рассинхронизацию при изменении контракта и
непроверяемость: каждую функцию нужно тестировать отдельно.

**Как правильно:** одна-две функции наверху превращают внешний ответ в типизированную структуру
или таблицу значений; дальше код работает с ней. Конвертацию типов делать платформенными
средствами (`XMLЗначение`, `XMLСтрока`), а не ручным разбором форматов.

### AI-09 · Резолв конфигурации и умолчаний внутри циклов 🟠

**Что искать:** вычисление настроек, поиск ссылочных значений по умолчанию, чтение констант —
внутри процедур заполнения и внутри циклов.

**Почему:** повторный резолв даёт лишние обращения к базе и размазывает ответственность: одна и
та же настройка вычисляется в трёх местах и в четвёртом забывается.

**Как правильно:** всё разрешается один раз при сборке контекста, до циклов; процедуры
заполнения выполняют плоское присваивание.

### AI-10 · Сопоставление в памяти вместо соединения в запросе 🟠

**Что искать:** вложенные циклы поиска соответствий и построение `Соответствие` для связывания
наборов, которые оба приходят из базы.

**Почему:** движок запросов делает это короче и быстрее.

**Как правильно:** одним запросом с временными таблицами и соединениями, затем
`ЗаполнитьЗначенияСвойств` — если выровнять псевдонимы колонок запроса под имена реквизитов
приёмника, заполнение становится однострочным.

**Не потеряй при этом:** проверку однозначности ключа соединения. Если ключ не уникален в
источнике, соединение размножит строки. Нужен либо контроль уникальности, либо явная
дедупликация.

### AI-11 · Потеря guard-проверок и побочных записей при упрощении 🟠

**Что искать:** в диффе — исчезнувшие проверки граничных случаев и исчезнувшие записи, которые
служили не результатом, а следом (идентификаторы, стартовые состояния).

**Почему:** сокращение кода не всегда улучшение, но и не всегда регресс. Опасна не сама
правка, а то, что удаление проверки происходит **незаметно для автора**.

**Как правильно:** при упрощении инвентаризировать удаляемые проверки и записи и по каждой
принять осознанное решение. Обратное правило тоже действует: не вешать ярлык «регресс» на
намеренное упрощение, не зная модели эксплуатации и инвариантов данных.

### AI-12 · Проведение внутри транзакции записи 🟠

**Что искать:** запись документа и его проведение, завёрнутые в одну транзакцию «ради
атомарности».

**Почему:** проведение проверяет остатки и может законно не пройти. Внутри общей транзакции
такой сбой откатывает всё и **маскирует причину** — вместо понятной ошибки проведения
получается пустой результат.

**Как правильно:** в транзакции — запись и сопутствующие следовые записи (они существуют тогда
и только тогда, когда документ записан). Проведение — отдельным шагом после успешной записи.
Тогда документ сохранён, а ошибка проведения видна и разбираема.

## Группа C. Механика платформы: конкретные грабли

### AI-13 · Поиск дополнительного свойства по наименованию 🟡

У плана видов характеристик дополнительных реквизитов **программное имя** и **пользовательское
наименование** — разные реквизиты. Библиотека резолвит свойство только по имени. Поиск по
наименованию работает случайно и ломается при первом же переименовании заголовка.

Правильно — запрос по реквизиту `Имя`, сразу пакетом для всех нужных имён, с получением
соответствия «имя → ссылка».

### AI-14 · Чтение ячейки табличного документа несуществующим методом 🟡

У табличного документа нет метода `Получить`. Ячейка читается через `Область(Строка, Колонка)`.

Для текстовых ячеек, пришедших из внешнего файла, читать нужно `.Текст`, а не `.Значение`:
свойство значения доступно, только когда в ячейке лежит объект-значение, иначе — ошибка чтения
поля. `.Текст` не выбрасывает исключение никогда, пустая ячейка даёт пустую строку; типизацию
выполняет вызывающий код.

### AI-15 · Присваивание read-only свойствам параметров записи 🟡

У параметров записи JSON свойства доступны только для чтения — значения передаются
**в конструктор**. Попытка присвоить свойство после создания объекта без аргументов даёт
ошибку недоступности поля для записи.

### AI-16 · Колонки неограниченной длины в запросе с группировкой 🟡

Колонка таблицы значений, объявленная как строка **без квалификатора длины**, имеет
неограниченную длину. Помещённая во временную таблицу и использованная в `РАЗЛИЧНЫЕ`,
`ОБЪЕДИНИТЬ` или `СГРУППИРОВАТЬ ПО`, она даёт ошибку выполнения: движок запросов не умеет
работать с полями неограниченной длины в этих конструкциях.

Колонки, которые попадут в запрос, всегда объявлять с квалификаторами. И не ставить
`РАЗЛИЧНЫЕ` там, где ключ уникален по построению.

## Что проверяется другими контурами

Часть уроков из того же источника относится не к коду, а к структуре программы, и живёт в
контуре `bsl-architecture-review`: доверие контракту собственной функции, единая точка
валидации вместо дублирующих проверок, единый расширяемый парсер вместо форка на каждый
вариант ответа, выделение подготовки данных в отдельный метод, проектирование
структуры-носителя под будущие поля, конструктор структуры-контракта.

Регистрация объекта метаданных в составе конфигурации проверяется контуром
`xml-structure-review`: файл на диске, не внесённый в состав, не попадает в сборку, при этом
ни загрузка конфигурации, ни валидаторы структуры этого не диагностируют.
